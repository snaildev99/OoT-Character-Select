# OoT (Switch 2) modding workspace

Game data: the extracted romfs at `%USERPROFILE%\Games\Hookshot\romfs` (from the Hookshot build). The game runs on the Tears of the Kingdom engine family: zstd files with dictionaries, SARC, BYML, AINB node graphs.

Python: `venv\Scripts\python.exe` (Python 3.11, with `ainb` and `pyzstd`).

## Tools

- `tools\nxfmt.py`: zstd (with the game's ZsDic), SARC and BYML readers.
- `tools\nxpack.py`: SARC file replacement; zstd compression with the same dictionary as the original file. Unmodified archives rebuild byte for byte.
- `tools\byml.py`: BYML read/write with exact scalar types; 19 of 21 RSDB tables rebuild byte for byte (ActorInfo: same content, different sharing; Tag: binary nodes, unsupported).
- `tools\msbt.py`: message (text) files. This game's MSBT text is UTF-8. All 540 US English files round-trip byte for byte.
- `tools\ainbx.py`: AINB load/save on top of the `ainb` package, with two writer fixes (transition indices, query order). 101 of 108 `Sequence` graphs rewrite byte for byte, every menu graph included; `ainbx.from_dict(d, like=original)` (editable dict form) 98 of 108. Not exact: `AfterChangeBanc`, `BeforeChangeBanc`, `DestroySceneCommon(.110)`, `ShortCut`, `UpdateShortCutOpenHoldFrameCounter`, `LoadBancImpl`, `BeforeInitializeCommon`, `BeforeTitle(.110)`; don't edit those with it yet.
- `tools\rstb.py`: the resource size table (read, change, write; rebuilds byte for byte).
- `tools\a64.py`: reverse-engineering helpers for the executable image (`image.bin`, loaded at 0x80000000; `main` starts at 0x80020000): string search, ADRP+ADD/LDR cross references, capstone disassembly, function bounds (`pacibsp`), per-function strings/calls. Needs `capstone`, `numpy` (installed in the venv).
- `tools\exepatch.py`: code patches for `main` as an IPS32 file (`exefs\<build id>.ips`; file offset = 0x100 + address - 0x80020000), with keystone (`keystone-engine`) assembly, checks of the replaced instructions, and a code cave in the zero padding after `.text` (0x83c661d0-0x83c67000). The emulator's built-in "Dynamic FPS by Dark" patch owns main+0x3C46200-0x3C46278 and is silently skipped if a mod touches it, so our cave starts at main+0x3C46C00 (0x83c66c00) with the signature words 1337, 69420. Build ID of v1.1.1 `main`: `E0F3CCFAF50065AE4EA01EB5AEB13B1A45DA3348`. Instructions keystone does not know (`retab`, `ldset w13, w14, [x12]`, `ldclr w13, w14, [x12]`) are listed in `exepatch.PSEUDO` and written by their name; never use `.long` inside assembly text: keystone then computes every later absolute branch target 4 bytes off per `.long`. `Patcher.rodata(name, blob)` puts tables in the zero padding after `.rodata` (0x8486c100-0x8486d000, `RODATA_CAVE`; one mod only, so far Character models in `--npcs`).
- `tools\bympatch.py`: in-place BYML edits that keep every existing byte (change inline ints, append a dict to an array; the grown array goes to the end of the file). For tables `byml.py` cannot rebuild exactly, like the GameDataList (big-endian; a rewrite comes out 13 KB larger).
- `tools\gamedata.py`: GameData flag hash (murmur3_32 of the full name) and the save-size bookkeeping rules.
- Code cave split between mods that ship their own `.ips` (all are applied together): `Header four tabs` 0x83c66c00-0x83c67000, `Character models` 0x83c66800-0x83c66c00 (`exepatch.CAVE_MODELS`); each part starts with the signature words. `build.py` refuses overlapping patches across mods.
- `tools\live.py`: live GameData flags and menu actors through the debug server (see the player-model section).
- `tools\livetrace.py <out file> [seconds]`: records the menu actor manager from the running game about 180 times a second through the debug server (read only), one line per value that changed: display type, camera block 0, our flags, and for the camera, menu slots 0 / 1 / 4 and the backdrop the actor's state, flag words, position and pending position request. Start it, do the thing in game, read the file (it settled the transition's version 2 in one press).
- `tools\package.py <version>`: the package for other people (2026-11-10): the five installed folders of the full build as `dist\OoT-Character-Select-<version>.zip` with `INSTALL.txt`, `SHA256SUMS.txt` and the code patches' listings. It refuses unless `build\` is byte for byte what is installed (i.e. what was played), leaves out the 10 Retro Link files (not ours to pass on; nothing in the package can ask for them), accepts data files only, and writes the zip with fixed dates and order, so the same build gives the same zip and sum.
- `tools\publish.py <folder>`: the public source tree (2026-11-10; pushed from `C:\Repos\OoT-Character-Select` to github.com/snaildev99/OoT-Character-Select): `mods\*.py`, `tools\*.py`, this file as `docs\NOTES.md` and `publish\*` (the public README with the package sums, the licence), with the author's first name replaced by the handle and profile paths without the user name; it fails if anything personal is left. Nothing of the game, no builds, no `assets`, no `research`, no session notes. Commits there use the account's no-reply address (set in that folder only). After a new package: put its sum into `publish\README.md`, run this, commit and push.
- `tools\bntxwrite.py`: adds textures to a layout archive's texture file (`add_textures(data, [(name, rgba)])`: ASTC 4x4 sRGB through the `astc-encoder-py` package, installed into the venv on 2026-11-10; the console's block order; the file's dictionary and relocation table rebuilt). Run by itself it checks the game's three files (see the layouts section).
- `tools\dbg.py` + `PLAY-debug.bat`: the emulator's debug server (`EDEN_NX2_DEBUG_SERVER=127.0.0.1:6545`, built into Fritchii): status, memory search and reads of the running game. Never screenshots.
- Signature values for things our mods add: header preset 1337, `CharacterMenu.module` blackboard ID 69420, node GUIDs `00001337-...`, code cave marker 1337/69420. Category stays 7 (the game uses it as a shift and a table index).
- `tools\extract.py <archive.zs> <out dir>`: unpack a SARC/blarc. `tools\strs.py <file>`: printable strings. `tools\grepimg.py <image.bin> <regex>`: strings in the game executable. `venv\Scripts\ainb.exe <file>.ainb`: AINB to JSON.
- `tools\layout.py`: UI layouts (`.buil`) as an object tree, read and write. All 164 layouts (Common, Title, ZeldaNotes, Boot) rebuild byte for byte, and also after moving every object (proves every pointer is known). Schema from the game's relocation code (see the layout section). `tools\uiedit.py`: editing on top of it: pane views (position, size, scale, visibility, ...), cloning a pane with what it owns, inserting pane blocks with every index renumbered (including the material / pane indices repeated inside picture, text, capture and list records), new animations (constants, Hermite / linear / one-key-per-frame "state" curves, driving a part's own animation with `drive()`), `anim_values()` (what an animation sets at a frame, for offline checks), text settings (`set_text`), colour palette, `pane_rects` / `part_bounds` (where a part's panes are, from the records), `validate()` (passes on all 164). `tools\bntx.py`: the UI texture archives (`Common...bntx.zs`: list, decode a texture to RGBA numbers, `stats()`; block-linear deswizzle, BC1/3/4/5/7, ASTC, RGBA8). `tools\cityhash.py`: CityHash64 (the layouts' name hash). `tools\sarcedit.py`: SARC rebuilt from its entry list, so files can be added (the layout and Mals archives rebuild byte for byte). `tools\uimap.py`: text map of every layout (`research\ui-map\`).
- `tools\uienv.py` + `PLAY-debug-ui.bat` + `install-ui.bat`: the UI sandbox's own emulator, a portable copy of the current Fritchii (hard links) in `C:\Repos\Lichii\dist\Fritchii-ui` with its own mods folder (`user\load`, set in its copy of the config), sharing saves (the config pins NAND/SD to `%APPDATA%\eden`; the emulator re-reads the user profile from there after loading the config, the stray `user\nand\...\profiles.dat` it writes first is not used), keys and shader caches (junctions). Its config is copied from the normal one on every install, with every mod of its own folder switched on. Its log is `user\log\eden_log.txt` (a hang shows as "Force stopping EmuThread" at shutdown without a crash before it). Debug server on 6546. Don't run it at the same time as the normal emulator.
- `tools\bfres.py`: model files (FRES v0.10.4): reader and skeleton editor (bone list, bone dictionary, matrix-to-bone table, the shapes' bone indices, inverse bind matrices, model rename). Edits never move existing data: new arrays and strings go where the relocation table was, the table (with entries for the new pointers) follows them. Checked on the game's files: the dictionary builder reproduces all 2,158 dictionaries of the character models byte for byte and its lookup is the game's; bone records round trip; rest matrices from the bone records match the stored inverse bind matrices (worst 1.1e-5) on all 129 `Npc_*` / `Player_*` models. `tools\npcrig.py`: an NPC skeleton as a player skeleton (see the NPC section) and `check_rig()`, the proof per file.
- `tools\npcenv.py` + `PLAY-debug-npc.bat` + `install-npc.bat`: the NPC characters build's own emulator, a portable copy of the current Fritchii in `C:\Repos\Lichii\dist\Fritchii-npc` (same scheme as the UI sandbox's: own mods folder, shared saves / keys / shader caches). Debug server on 6547. `tools\npclive.py`: logs the stored character number and the menu actors of that copy during a test (`build-npc\live-log.txt`); memory reads only; one logger serves a whole session (after a game closes or crashes it waits for the next).
- `tools\npcportrait.py` + `tools\npcportrait_blender.py` (experiment, 2026-11-10): character portraits on a transparent background, rendered outside the game. Step 1 (normal venv) writes a model's rest-pose geometry and decoded textures as arrays to `build-npc\portraits\<model>\` (vertex and index buffer layout in the file's head; smooth shapes are stored in model space, eyes are rigid to their bones; some texture names in a model do not exist as files, e.g. Saria's `Mt_Eyebrow_<model>_Alb`: the shared `Eyebrow_CmnTex_Chara_*` is used; eyebrow and eyelash colour textures are grey masks; eye textures are shared: sclera everywhere, the iris in the middle 0.27 of the eye's uv square by the mask texture, uv centre = front of the eyeball). Step 2 (`venv-blender`: Python 3.11 with `pip install bpy==4.5.16`, Blender as a module, 720 MB, nothing installed system-wide) renders head and shoulders twice, `build-npc\portraits\<name>_studio.png` and `<name>_cinematic.png` (1024 x 1024), and prints coverage, brightness and eye / cheek probe numbers. The materials are approximations of the game's shader (list in the tool's head); whether the result is good enough is snaildev's call, otherwise portraits come from the game.
- `tools\npcshots.py`: saves game frames during the portrait run (see the NPC characters entry); reads memory and asks the emulator for screenshots, presses nothing.
- `tools\npccutout.py`: cut-out portraits from those frames (pairs the last black and the first white frame per character, transparency from the difference in linear light, head-and-shoulders square from the model's Head bone height); needs Pillow (in the venv). Prints numbers only.
- `tools\npcauto.py`: NOT IN USE, never run against a game: snaildev tests in the game himself (2026-11-09: "No, I'll test it myself"); don't run it or start an emulator unless he asks. What it is built on: the debug server can press buttons too: method `input_sequence`, steps `{"buttons": [...], "left_stick": [x, y], "right_stick": [x, y], "frames": n}` on player 1, counted in presented frames (at most 1,000 steps / 36,000 frames per call; buttons A B X Y L R ZL ZR Plus Minus Up Down Left Right StickL StickR), plus `log_tail` (`after`, `limit`, `contains`) and `status` (presents, fps, paused). (Methods known from the emulator source `src\core\debugger\nx2_debug_tools.cpp` and the strings in Fritchii 5.5's exe, not from use.) The tool's design: its own emulator copy (`...\Fritchii-npc-auto`, debug server 6548; removed again) that shares nothing a person's emulator writes (own save copies, own empty shader cache, sound off, no physical controller, window minimized), `ring` = D-pad right through the character ring with a memory check after every swap, `field <number>` = write the number into its save copies (`progress.sav`: the flag's hash, then the value; verified on copies: one byte changes), boot, run / roll / swing / guard.
- `tools\seqmap.py` (field swap session): every sequence graph as a compact text outline, one line per node (index, node name, inputs as `name=value` or `name<-node.output`, `~` = left at the declared default, properties that differ from the usual, children / transitions): `venv\Scripts\python.exe tools\seqmap.py research\seq-map` writes `research\seq-map\<graph>.txt` for all 108; `--find <text>` lists the nodes of all graphs that mention a text (a node name, a screen, a flag). Read only.
- `tools\fieldenv.py` + `PLAY-debug-field.bat` + `install-field.bat`: the field swap build's own emulator, a portable copy of the current Fritchii in `C:\Repos\Lichii\dist\Fritchii-field` (same scheme as the UI sandbox's and the NPC build's: own mods folder, shared saves / keys / shader caches, every mod of its folder switched on at each install). Debug server on 6549. `tools\fieldlive.py`: logs that copy during a test (`build-field\live-log.txt`): the stored character, the "swap pending" flag, the counters and the remembered position our routines keep, and (once a swap has run) every resident actor's state; memory reads only; one logger serves a whole session. `tools\fieldcam.py [seconds]`: records the player camera around a swap about 600 times a second (the camera system object, the camera actor's pose, its component's 0x1200 bytes, the view, the player's pose and camera part, our counters) into `build-field\cam-trace.pkl` (`fieldcam.load()`), notes in `build-field\cam-trace.txt`; memory reads only; it ends when the game closes; don't run it together with `fieldlive.py`.

`research\` holds the menu graphs (`menu-ainb-json`), the Common UI layouts (`layouts-common`), and lists of screen classes and sequence nodes found in the executable.

## Mods

`install-mods.bat` (= `mods\build.py --install`) builds every mod in `MODS` from the untouched romfs into `build\<mod>\romfs`, copies it into `%APPDATA%\eden\load\0400486024DEC000\<mod>` (shared by all emulator builds) and removes retired folders. It refuses while the emulator runs. Each mod asserts the original values it changes; files that grow or are new get entries in one combined size table, shipped as identical copies in `Characters page` and `Character models` (whichever the emulator picks has every entry; new paths are checked for crc32 collisions). New graph nodes get stable GUIDs, so rebuilds are identical.

- `Characters page` (`characters_page`): L/ZL on Key Items -> Key Items' exit animation (`CloseAllMinusMenuContentScreen` with `IsCloseImportantToChallenge`), "tab left" sound, loads our screen -> `Prev`. `MinusMenu.module` routes `Prev` of both ImportantMenu nodes to a new module node `CharacterMenu.module` (Next -> ImportantMenu node 20, Main -> 4, PouchMenu -> 24, Event -> 12). `Sequence/CharacterMenu.module.ainb`: opens screen `CharacterMenu_00` with `InFromChallenge`, applies env set "Pouch", display type 0 (3D Link); R/ZR -> `InChallenge`, close + unload -> `Next`; B/− (if closable) -> `Main`; `MinusMenuToMain.module` closes + unloads `CharacterMenu_00` (if open) in its `CloseScreenWithPauseMenuBG` step, the same frame as the header and the other pages. New row `CharacterMenu_00` in `RSDB/UIScreen` (placeholder layout `ImportantMenu_01`, no class, draw unit 1, sort key 5000, loaded on demand, `IsHeapReverse`). Y / X (`CHARACTER_BUTTONS`): set `CharacterMenu_SelectedCharacter` to 0 (Link) / 1 (Retro Link) and rebuild the menu's 3D Link, one step per frame (`IsUpdateNextInFrame` false): set `CharacterMenu_KeepUICamera`, display 4, `SeqOneShotDeletePouchPlayer`, wait, `SeqOneShotCreatePouchPlayer` child/adult by `Sequence_IsChildhood`, wait, `SeqSyncPlayerEquipmentAndGameData` pouch only, `WaitEquip.module`, `SeqOneShotCreateUICamera` if the area uses one (a no-op while the camera is kept), wait, display 0, clear the keep flag; checked after B/−/R/ZR. Works in game (snaildev, 2026-11-09), with a dark overlay while the view is hidden. For other graphs (the UI sandbox) `character_swap_steps()` returns the same steps as one nested sequence that runs one step per frame whatever the caller's sequence does. Without display 4 (tried on D-pad Left / Right) the overlay looked the same, so it is not the hidden view. The overlay is the floor spotlight of the menu scene turning black from the moment the old Link is deleted until the new one shows (same shape and soft edge as the spotlight; snaildev, 2026-11-09): the menu lighting needs Link present, most likely his shadow (no caster -> the spot reads as fully shadowed). With set / delete / clear of the keep flag in one frame the camera was still deleted, so the steps run one per frame and the flag stays set until Link is shown.

- `Character models` (`character_models`, flag + models + exe patch, separate so it can be switched off alone): GameData Int `CharacterMenu_SelectedCharacter` (hash 0xd6b580ea, saved in progress.sav, ResetTypeValue 8, default 0), appended to the GameDataList in place with the save-size bookkeeping. Second flag `CharacterMenu_KeepUICamera` (Bool, not saved): while set, a patch at 0x80c35c64 skips the camera part of the game's "delete the menu Link" (only the Characters page sets it, around its delete step). Third flag `CharacterMenu_IsPageOpen` (Bool, not saved), set when the Characters page opens and cleared on R/ZR and in `MinusMenuToMain`'s step that hides the 3D view (display 5). While set, a patch at 0x8289d1b8 in the 3D UI camera update (`view_hook`; the update loads the menu manager's camera block +0x22c + 0x38 * display type: position, aim point, up, near, far, fovy and 8 more bytes) puts Link on the right third for the UI (snaildev, 2026-11-09). `VIEW = "lens"` (default): the 8 bytes after fovy are the **projection offset** (x, y floats, copied to the camera at +0xcc after the aspect ratio); an offset o moves the picture by -2 * o half screen widths (in game: +1/6 put Link on the left third, -1/6 a little left of the right third), so -(1/3 + 0.07 / 1.412) / 2 = -0.1915 puts Link's origin on the right-third line with the camera where the game has it (Link looks exactly as in the game's own view). `VIEW = "camera"` (passed in game first): camera and aim point moved by -0.541 m instead (half screen width at Link = tan(10 deg) * 4.504 * 16/9 = 1.412 m); Link is then seen from 7 degrees to the side. - Field Link is a "resident actor": `LoadBancImpl` creates it with `SeqExecuteSceneRequestCreateResidentActors(IsCreateChildPlayer = Sequence_IsChildhood)`. Normal area changes only put it to sleep (`SleepResidentActor.module`); it is deleted only by `ChangeBanc` with `IsDeleteResidentActorsBeforeDestroyBanc` (only the Opening sets it), by return to title (`PlusMenuToTitle`) and on scene destroy. - Layers (live 2026-11-09): manager `[0x84ea1cf0]` (+0x20 count, +0x28 array of 32); a layer's viewport is floats at +0x30 (min x, y) / +0x38 (max x, y) in 1280 x 720 units, render info at +0x80 (aspect at +0xb0). Tags -> layer index via `[[0x84eb50a8]+0x38]` (groups at +8, mask +0x108; each a sorted tag list and the layer index at +0x38). The menu 3D layer (tag 0xb9f65e9a = -1175036262, also the 3D UI camera's LayerTag) was layer 6; the main layer tag 0x1b6ce343 (460120899) layer 0.
- Debug server: the game's `main` runs 0xacb000 above the image addresses (live 0x80aeb000; find it by searching memory for code bytes from `image.bin`), so a global at image address A is read at A + 0xacb000. `tools\live.py` finds the shift itself and prints our character flag and the menu actors (handle ids, names, positions); its GameData lookup is the same as the model hook's.
- GameData: `GameData/GameDataList.Product.110.byml.zs` (big-endian BYML): per type an array of {Hash, DefaultValue, ResetTypeValue, SaveFileIndex (-1 not saved, 0 progress.sav per slot, 1 option.sav, 2 caption.sav, 3 account.sav)}; arrays are not sorted. Hash = murmur3_32(full name), e.g. `Sequence_IsChildhood` 0xcea220d3. Sequence nodes: `SeqOneShotSetNonStructGameDataInt` / `SeqQueryGetNonStructGameData*` (by `GameDataFullName`).
- GameData in memory: manager = `[[0x84c9e180]]` (GOT entry). Bool: hash map +0x20 (capacity +0x2c), records +0x18 (count +0x10, 0x18 bytes, value byte +0x16). Int: hash map +0xe0 (capacity +0xec), records +0xd8 (count +0xd0, 0x28 bytes, value +0x1c). Hash maps: {u32 hash, u32 record index}, open addressing from hash % capacity, empty slot = hash 0.
- GameData sets from sequence nodes are queued, not written at once: `SeqOneShotSetNonStructGameDataInt` by name ends in 0x80183b70(manager, value, hash), which appends (value, hash) to a fixed-size queue (entries at +0xf8, capacity +0xf0, counter +0x100) applied later, and jumps to an abort stub (0x8351c280) when the queue is full. So a flag set is not visible to code in the same step (why set / delete / clear of the keep-camera flag in one frame did nothing), and a sequence that sets a flag and returns to a button loop in the same frame, while the button trigger is still set, loops until the game aborts ("Userspace PANIC" on D-pad Up, 2026-11-09). Put a `SeqExecuteGenericWaitFrame` (template: FastLoadOn node 4) after such a set, or spread the steps over frames (`IsUpdateNextInFrame` false).
- Emulator log (`%APPDATA%\eden\log\eden_log.txt`): `Module rtld loaded at X (size 0x20000)` gives main = X + 0x20000, so crash backtrace addresses map to image addresses by subtracting (X + 0x20000 - 0x80020000).
- Reset: `SeqExecuteResetGameData ResetType=N` resets flags whose ResetTypeValue has bit N (most saved Ints: 8 = bit 3, reset by `NormalTitle` ResetType 3). Scene destroy (`DestroySceneCommon`, e.g. return to title) resets ALL game data (`SeqExecuteResetGameDataAllForDebug`, runs in retail unless the debug flag `IsSkipForceResetGameData` is set), so a flag that should survive return to title must be saved.
- Save files (`%APPDATA%\eden\nand\user\save\0000000000000000\<user>\0400486024DEC000\slot_NN\progress.sav`, `option.sav`, ...): header 0x20 (magic 0x01020304, version 0x002d80eb, offset of the variable data), then per type a marker (0, type index) and (hash, value) pairs, then the variable data (Bool64bitKey flags, arrays, strings), then the file's SaveTypeHash. The loader (0x80bc26c0) looks each hash up and keeps unknown ones aside (0x8378c050 / 0x8378ce10), so new flags don't break old saves and saves with extra flags still load in the stock game. Bookkeeping per extra scalar flag: `AllDataSaveOffset` / `AllDataSaveSize` +8 (AllDataSaveOffset = 0x20 + 8 * (all flags except Struct, BoolExp, Bool64bitKey + 34)), and `SaveDataOffsetPos[f]` / `SaveDataSize[f]` +8 for its save file f (SaveDataOffsetPos[0] = 0x20 + 8 * (file-0 flags except Bool64bitKey + 34) = 95704, matches the save header).

## What we know about UI layouts (.buil)

- File: `BFFH` header (u32 size at +8, section table at +0x10: `BFSI` entries {u32 offset, u32 size, u32 align, u64 offset, name[16]}, root at 0xf8, type name `Nintendo.Ui.ResModels.LayoutResData` at +0x28), section `Default` (objects) then `StringPool` (C strings and 6-byte animation keys). Pointers are u64 file offsets; the game relocates them in place by walking every reference by type (`LayoutResData` relocator 0x8153e804; material 0x8153e5e0, picture data 0x8153e720, part 0x8153f900, slide-list part 0x81540000, pass 0x8153fb40, animation 0x8153fec0 -> 0x815723e0 -> curves 0x815722e0, whose two keys objects are relocated by type-word handlers; every vanilla curve has type 0). Objects are written depth first in field order; arrays are {u64 ptr, u32 count, u32 stride}; dictionaries are {keys, values, hashes, count, stride} written as values, keys, hashes, 32 zero bytes, then the objects; hash = CityHash64 of the name. Strings enter the pool in visit order (deduplicated).
- Root (0x228): name +0x18; dictionaries in pane order: panes +0x20 (record 0x44), materials +0x40, pictures +0x60 (P_ and W_), texts +0x80 (0xa8: font, size, text, message ref), alignments +0xa0, parts +0xc0, captures +0xe0, slide lists +0x100, animations +0x140, window extensions +0x160, capture textures +0x180; passes (shader setup with texture names, archive "ui") +0x130, colour palette +0x1c8 (RGBA floats; materials index it), float palette +0x1d8, pane alpha table +0x1e8, name table +0x1f8 (names of things inside the layout's parts that are referred to by index: part animations driven from here, part panes whose properties an instance overrides), per-material u32s +0x208, screen size 3840x2160 at +0x200.
- **Typed records repeat their pane's indices** (100 % on the 164 layouts): picture +0x10 = material index; text +0x88 = material, +0x8c = pane index; capture +0x0 = material, +0x4 = pane; slide list +0x28 = pane; part +0x40 = pane. After any insert these must be rewritten for every later pane (`uiedit` does since 2026-11-09; the first sandbox layout had 81 stale ones, e.g. the fade overlay pointing at another pane's material).
- Pane: +0x10 scale, +0x18 rotation (radians), +0x1c translate (y up, centre of screen = 0,0), +0x24 alpha table index, +0x28 parent, +0x2c size, +0x34 end of subtree, +0x38 flags (bit 0 visible, (flags >> 7) & 7 = type: 0 null, 1 picture/window, 2 text, 3 alignment, 4 scissor, 5 capture, 6 part, 7 slide list; bits 12+ two-bit anchor fields), +0x3c material | window-extension << 16, +0x40 type index << 16. Each material owns a run of passes (1 for pictures, 5 for texts) from material +0x14.
- Part instance record: layout name, overrides, property paths (start with the part's own pane index as a string), initial frames of the part's own animations ({name, f32 frame}; e.g. `ItemPattern` picks an equipment button's icon, the header's tab shapes), text overrides, own pane index at +0x40.
- Texts (from the code: text resolver 0x837a0cd0 -> label builder 0x80791bb0, message file `LayoutMsg/<name the screen returns>.msbt` built at 0x80459950, in `Mals/<lang>.Product.110.sarc.zs`): the reference string (text record +0x18) decides. `*` or a null pointer: the label is the pane's path, the names of the part panes it sits in and its own name joined with `-` (`Pa_Parts_00-T_Icon_00`; 0x80791d40). `%Label`: that label. `=path`: the label of another pane (`=T_Btn_00`, `=../../Pa_HeadEquip_00/Pa_Guide_00/T_Guide_00`). `&`: a path with `/`. Anything else, `@...`, `-` and also a non-null empty string as the builder is written, gives no lookup: the game's code sets the text, or it stays empty. Vanilla panes with an empty reference do have path labels in the message files (`Pa_CheckButton_01-T_Btn_00`), so the empty case reaches the builder as a null pointer somewhere we have not read; use `*` for our own panes. A part instance can replace the reference of a text pane inside the part (strings in its record at +0x38, picked by 24-byte override entries at +0x8 whose key names the pane through the name table and whose type is 0x19; e.g. `@T_Btn_00`, `-`); not decoded far enough to write. Text record: +0x08 font size x/y, +0x70 and +0x78 horizontal alignment (0 left, 1 centre, 2 right), +0x74 vertical (0 top, 1 centre, 2 bottom), +0x7c / +0x80 spacing floats, +0x38 / +0x54 / +0x58 colour palette indices.
- Colours: a material's +0x18..+0x24 are four colour palette indices (corners), +0x28 the white colour and +0x2c the black colour: the texture's grey is mapped black -> white. Threads of Time's entry diamond (`PaChallengeIndex_00`): `P_DotBase_00` (texture `ChallengeIndexDot_00`, 80 x 80: opaque frame, dark middle; white = palette 5, dark brown) is the empty diamond; `P_Dot_00` (`ChallengeIndexDot_01`: a smaller grey ramp; black -> white = palette 7 -> 6, (0.738, 0.074, 0.014) -> (1, 0.212, 0.09), deep red to orange red) is the gem inside. No animation shows or hides `P_Dot_00`: the game's code does. `ChallengeState` 0 / 1 / 2 = diamond shown / hidden / hidden with the title dimmed; `ChallengeType` 2 = indented entry; `Select` 0 -> 4 = cursor in.
- Pane flag bits 12-23 are two-bit fields: 12-13 base position horizontal (0 left, 1 centre, 2 right), 14-15 vertical (0 top, 1 centre, 2 bottom), 18-19 / 20-21 which edge of the parent the position is measured from (same values; read off vanilla data, e.g. gauges that grow from the bottom; not confirmed in game), 16-17 and 22-23 unknown (1, sometimes 3). A part's footprint: its `B_Hit_00` when it has one, but some hit boxes cover only part of what is drawn (`PaOptionBtn_00`: 816 of 1880 wide) and some base pictures are far larger than the visible shape (equipment / item slots: 700 x 700 picture, 220 x 540 hit box). Part instance pane sizes look like editor bounding boxes (fractional values) and nothing is known to use them.
- Scissor panes (`S_`, type 4, flags 0x0255522b: a null pane's + type + bit 5) clip their children: Ocarina's melody strip is scissor -> null pane that scrolls -> parts, the pattern the sandbox list copies.
- Animations: Anim (0x30) -> data (name, targets, curves, per-curve component bytes, constants, per-constant component bytes, frame range), part-animation events, frame count +0x28. Target key: b0 sub element (0x7f = the pane), pane = ((b1 >> 3) & 15) | (b2 & 31) << 4, b3 property (0 scale, 1 translate, 2 visibility, 4 alpha, 27+ material colours etc., 57+ text, 0x43/0x44 with b4 = 1 = frame / enable of a part's animation). Target: first curve, first constant, count (curves | constants << 8), value type (0 bool, 12 alpha/normalised, 14 float, 15 colour). Component bytes: offset in the value (0 x, 4 y, 8 z, 12 w). Curves are Hermite keys (times; value, slope pairs; doubled keys for slope changes). A layout animation can drive a part's own animation: b0 = index in the name table (root +0x1f8), the animation lists an event (name, pane index, 1) per driven part, the frame is normalised (0 = start, 1 = end; vanilla uses 0.5 for frame 1 of a 2-frame state animation), usually a curve, a constant 1.0 in 8 places. Verified on all 3,661 vanilla targets. The key is a 7-bit-per-byte bit stream (decoded at 0x81505fd8): sub element 10 bits (b0 | (b1 & 7) << 7, all ones = the pane), pane 10 bits ((b1 >> 3) & 15 | (b2 & 63) << 4; bit 9 is always set, so the index is the low 9: a pane with an animation target needs an index below 512, and inserting panes moves the ones after them, so keep a layout with animations under 512 panes; `uiedit` asserts it), property 9 bits ((b2 >> 6) & 1 | b3 << 1 | (b4 & 1) << 8): "b3 = 2" with b2 = 0x60 is visibility, with b2 = 0x20 it is the pane size (value type 13). Curve type word (+0x10): 0 clamp, 0x0400 repeat (the curves of looping animations), 0x0480 a second repeat kind; animation data +0x58 = 1 marks a looping animation (59 of 781). The two 40-byte objects at animation +0x8 / +0x10 are zero in every file.
- Animation runtime (0x802f1380 = a screen's update; requests from `SeqOneShotRequestPlay / StopAnimationScreen` are objects inside the graph node, queued on the screen and run in the order they were issued, at most once per node per frame): play (0x802ee030) and stop at a frame (0x802f2d90; ignored when the frame is beyond the animation's length) both set the frame, enable the animation and move it to the END of the screen's list of active animations. Each update walks that list in order: apply the animation at its frame (0x802f2c20: its own targets, then the part animations it drives, recursively), then advance it if it is playing. A stopped animation is applied once, then disabled and taken off the list; a played one stays until a frame or two after its end. So what an animation wrote stays until another one writes the same property, a later request wins inside a frame, and state can be kept in many independent animations ("stop at frame n" = show state n). Animations are found by name with a linear scan of the CityHash64 values, then a string compare (0x8045c870): order and position in the dictionary do not matter. More from the code (2026-11-10): a play request plays with the loop mode of the animation's own flag (0x80bcce80 reads animation data +0x58 bit 0 and passes it to 0x802ee030, which stores it in the entry at +0x16: 0 once, 1 wrap, 2 back and forth); at the end a wrapping one has its length subtracted from the frame and goes on. Applying an animation (0x802f2c20) does nothing unless its enable bit (animator +0x1c bit 0) is set, applies its own targets, then calls itself for each part animator it drives whose enable bit is set: a part animation driven by a screen animation is applied exactly when that screen animation is applied, at the frame its targets just wrote. So two screen animations can drive the same part animation (or two part animations that write the same panes), and while both are active the one requested later is applied later and wins.

## What we know about NPC models, skeletons and animations

- Model files: `Model/<project>.<fmdb>.bfres.zs` hold one model named `<fmdb>` (FRES v0.10.4; layout in the head of `tools\bfres.py`: header, relocation table `_RLT` whose entries are grouped by the section the pointer points into, length-prefixed strings, dictionaries = Patricia tries over the name read as a big-endian number, FMDL 0x78, FSKL, bones 0x58, shapes 0x60). The header's "first block" u16 is the string pool offset cut to 16 bits, so nothing can be using the block chain. 5 models also exist as `.bfres.mc` next to the `.zs`.
- Bones: Euler XYZ rest rotations (skeleton flags 0x1200, scale mode Maya), world = parent x T x Rz x Ry x Rx x S; the inverse bind matrices (one per smooth matrix) are exactly the inverse of that. Flag bits 26 / 27 ("rotation / translation is zero") are hints that are sometimes clear although true, never the other way round. Rigid matrices (eyeballs) and weightless shapes use the bone's own frame for vertices, so such a bone's rest frame cannot change without touching vertices. Three models have a scaled bone (adult Link `Ph_Knee_L/R`, child Ruto `Ph_Neck_Assist`), always a leaf.
- The humanoid rig is shared: 98 `Npc_*` models have Link's names for the 60 body joints (Skl_Root, Spine_1/2, Neck, Head, Waist, per side Clavicle, Arm_1/2, Wrist, the 19 hand bones, Leg_1/2, Ankle, Toe) with Link's local frames (child joint on +x and so on). Exceptions found by comparing rest rotations with Link's: the upper arms (Link is modelled arms down 45 degrees as a child, 35 as an adult; 77 models arms level, the Gorons 10), child Malon's waist (120 degrees: another frame, compensated in Leg_1), `Npc_Hylia_MM_003`'s legs (90-139), Dampe's and `MU_004`'s bent neck and head (54-88: a pose, not a convention). Bones of the same name outside those joints are NOT the same thing: `Hair_Root` (120 / 180 degrees in 23 models), the `Ph_` cloth, sleeve, skirt, collar and hair bones (90-180), child Link's eyelid bones against everybody's (71-110), face bone positions (child Link against Saria: median 9 mm, eyelids 48 mm).
- NPC skeletons lack what the player's data and code name: `Head_2`, `Pod_A`, `Weapon_Root`, mostly `Pod_B`, sometimes `Ear_*` / `Weapon_L/R`, and Link's own cloth / helper bones. Names used: `EquipmentUserParam` (Weapon_R, Weapon_L, Pod_A, Pod_B, Ph_Bangle, Spine_2; its material group lists name materials Link does not have, e.g. the typo `Mt_Earrinig`, so missing materials are tolerated), the player's `.asb` (Skl_Root, Spine_1/2, Head, Head_2, Neck, Face_Root, Mouth_Root, Waist, Leg_1_L, Arm_1_L, Weapon_L, Pod_A, Eyeball_L, the partials Lower / Upper / Face), the Phive files in the actor pack (cloth, `HelperBoneParam` with 119 bone names, foot / hand / look IK, eye bone kinematics), and about 30 bone names as strings in the executable (defaults of parameter structs).
- Animations: `Model/<project>.anim.bfres` (skeletal animations FSKA 0x50 each at header +0x58, count +0xe2; bone animations 0x38: name, curves, base values, flags with base S/R/T bits 3-5 and curve bits 6-15). They are stored unbound (bind index 0xFFFF for every bone, no bind skeleton) and bind by bone name at run time; packs are shared between models with different skeletons (the Kokiri girls use Saria's set with 151 of 249 bones in common). A bone animation writes absolute local scale, rotation AND translation: every bone animation of Link's packs (child 1,843 animations / 277 bones, adult 3,102 / 295) has base values for all three, so a bone of the same name takes Link's offsets. Curves on translation: Skl_Root (hips), the face bones (half of the animations), Pod_A, Weapon_Root, a few helper bones; the body joints' offsets are constant apart from Leg_1 / Waist / Toe in a handful.
- The engine can retarget: `AnimationParam.AnimationResources[i]` has `IsRetarget`, `RetargetModel` (default "Skeleton" = the file `Model/<animation project>.Skeleton.bfres`, a model with only the skeleton of the set's main character; 55 exist, e.g. `Player_Child_Demo_Animation.Skeleton` = Link's skeleton) and `IgnoreRetargetRate` (struct 0x50: project +0x38, RetargetModel +0x40, IgnoreRetargetRate +0x48, IsRetarget +0x49; read at 0x83b18fa8), and a component `RetargetScale` (per animation name a Scale vector). 15 AnimationParams use it: child Epona on the adult's set (bone lengths 0.32-0.76), Nabooru on the generic Gerudo set, Biggoron (15x), Medigoron (4.5x), Darunia's son (0.6x), the big Stalchild (1.6x) and Leever (1.44x), Ingo. In all of them the rest rotations are equal (Nabooru's arms differ by the 45 degrees of the modelling pose, and she is animated right), so it deals with lengths, not frames. The player does not use it; our rig does the same job in the model file instead (below), which leaves the actor parameters alone.
- What `tools\npcrig.py` makes of an NPC skeleton (per Link age, verified per file by `check_rig`): (1) the joints stay bound: each takes Link's rest rotation as its own (the frame turns, the inverse bind matrix follows, the mesh stays), so Link at rest = NPC at rest and Link's turn of a joint is the NPC's; the upper arms keep their own frame (so they hang as Link's do), and so does a joint a rigid shape hangs on. Each joint gets a static parent `Fx_<name>` holding (NPC offset - Link offset), which the animation's own offset completes to the NPC's: limb lengths, shoulder and hip width and standing height stay the NPC's. (2) every other bone that shares a name with a Link bone becomes `Nx_<name>` and keeps its rest pose (face, hair, cloth static). (3) every Link bone still missing is added without weights under Link's parent with Link's values (attach points, face, cloth and helper bones). World rest positions of all NPC bones are unchanged. Hips: Link's hip height + a constant, not scaled by leg length (a taller character floats in crouches and rolls; scaling needs scaled bones around Skl_Root and is not tried).
- A model file with the external file `LoadAttachAnim.flag` (0 bytes; Link and every NPC have it) also gets `Model/<project>.anim.bfres`: Link's has `Player_Child_FacialCheck` and one material animation on `Mt_Hairs`, an NPC's `<model>_1stModelPose`. Materials are named alike across characters (`Mt_Face`, `Mt_Skin`, `Mt_Eye_Inner`, ...), but the hair is `Mt_Hairs` only on Link (both ages) and child Zelda: 87 of the 98 humanoid NPC models have `Mt_Hair`, 10 no hair material (Zoras, bald men).

- Sequence node classes in the executable (code). The name getter is vtable slot +0x98 (three instructions: adrp, add, ret), so name string -> getter -> the one pointer to it -> vtable. Slots: +0xe0 registers the inputs (0x82633920, a bare `ret`, = no inputs; a Bool is registered with 0x803f94c0(node, &name, node + 0x20, 1, 0) and read as `[[node + 0x20]]`), +0xe8 enter, +0xf0 update, +0xf8 exit, +0x138 the body of a one-shot node (called by the shared one-shot enter 0x832e9ae0; the shared one-shot update is empty, so a one-shot runs once). x0 = the node. `[node + 0x18]` bits 30-31 are the state: an Execute node sets them to 2 when it is finished (`0x80000000 | low 30 bits`); stock updates start with vtable +0x80 (0x8002c800: the state) and do nothing when it is 2; the stock create node's enter clears the bits first.
  - 122 Execute / one-shot classes are in no stock graph, and none of them has an entry in `Sequence/NodeDefinition` (which lists exactly the 433 used ones). A class can be created from a graph only if it has a creator (a routine that allocates the node and stores the vtable) whose address the node factory takes (registration code around 0x81086900-0x81088000 and 0x8118e000): the classes whose vtables are at 0x84c8.... (code at 0x83bc.... / 0x83bd....: `SeqExecuteWaitFrame`, `SeqExecuteSwitchInt`, the `SeqExecuteUIPrototyping*` nodes, `SeqExecuteWaitGlobalResidentEventLoad`, a second `SeqExecuteWaitEventStart`, ...) have NO creator: their vtables are never stored anywhere, a graph cannot have them. (The check: `a64.Image().xrefs(vtable)` is empty.) `SeqQueryControllerReleaseMaskChecker`, which the picker uses, has one (0x8330f2f0, taken at 0x8108ca68).
  - Unused classes that can be created, have routines of their own and no or one simple input: `SeqExecuteCommitSave` and `SeqExecuteWaitCullingReady` (no inputs; the second has only an update of its own), `SeqExecuteWaitInitializeEventMgr` (one Bool, `IsNeedWaitResidentEvent`; enter is a bare `ret` at 0x832e74c0, update 0x832e74d0; creator 0x832e7470): the field swap takes this one over.
  - Room for code that no cave has: the bodies of unused nodes. `SeqOneShotSetGameDataAppearScarecrowFalseAll`'s one-shot body, 0x83302000-0x83302300, is one function of 0x300 bytes that only its vtable points at (the field swap uses 0x83302000-0x83302194). `mods\field_swap.py`, `check_dead_code`, is the test for such a region: its bytes are the ones the patch was written for, no jump or call from outside lands in it, no pointer but the vtable's, no address taken.
- Writable memory of our own: main's `.bss` ends at 0x84eba4c8 (MOD0 header at 0x83c6705c: bss 0x84d66b80-0x84eba4c8) and the page goes on to 0x84ebb000, mapped and zero.
